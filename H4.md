<h2>A01:2021 - Broken Access Control</h2>

This reading describes Broken Access Control that is now considered the number-one risk on the OWASP Top 10 list of web security risks. It is the most widespread type of vulnerability in current applications.

<h2>Summary</h2>

The Issue: The access control is the bouncer to an application. Once broken, users are allowed to step out of their intended permissions, that is, seeing, editing, or deleting data that is not their own.

The Scope: It applies to 94% of the applications found in testing and has more than 318,000 instances in current datasets. It comprises such risks as sensitive data exposure (CWE-200) and CSRF (CWE-352).

Common Failures: Insecure Direct Object References (IDOR)

Elevation of Privilege: A non-admin user obtaining admins or an unauthenticated user bypassing the log-in screen.

Metadata Tampering: Altering cookies or JWT tokens in order to deceive the server into believing that you are cleared.

Comment: Broken Access Control is a logical error than a syntax error.

Question: If the server requires a login to see the page, why can an attacker still access someone else’s data just by changing the account number in the URL?

<h2>A05:2021 - Security Misconfiguration</h2>

The current topic on this text is Security Misconfiguration, which is now in the OWASP Top 10 of rank 5. With systems being moved to the cloud, and depending on complicated stacks, there has been an explosion of buttons and switches to press the wrong ones.

<h2>Summary</h2>
The Issue: It is not always a bug in the code, but a malfunction of locking the doors and windows of the environment the code has been implemented into like its server.
The Scope: The misconfiguration of some kind is present in approximately 90 percent of applications. This is what the hackers use.

Common Failures: Default settings where admin/admin is used as user-name and password on a live site.

Long Error Messages: Which displaying an inner workings of code to a user upon a crash. It provides an open door for attackers.

Cloud Leaks: Giving public access to unconfigured S3 buckets or cloud storage accidently.

Missing Headers: The inability to inform the browser about how to behave safely by using security headers.

Comment: Many developers use codes of others and reuse it, this makes it easy for hackers.</br>

Question: If I keep my code 100% bug-free, can my app still be hacked through a misconfiguration?</br>

<h2>A06:2021 - Vulnerable and Outdated Components</h2>

This is the area of Vulnerable and Outdated Components which is now ranked, position 6. This type is peculiar in the sense that it is no longer about how you have written your code, but on the security of building blocks (libraries and frameworks) to which you have settled.

<h2>Summary</h2>

The Issue: Apps of today are not designed as such anymore, but rather assembled like LEGOs. Should you have a hole in one of your bricks that you downloaded, your whole edifice is in danger.

The Scope: This is an invisible murderer since, most developers do not even know that a single library they imported has 50 hidden dependencies, which they had no idea existed at all.

Typical Failures: The "Update Paradox": It is common in organizations to take months to patch systems because of the fear of change control that leaves a window open to hackers.

Unmaintained Code: Library that was three years in the past and the original developer abandoned it. No one is coming to repair a bug that is discovered today.

Shadow Dependencies: You do not know what releases of the software that are actually running in your server or within the browser of your user.

Comment: We are at the point where 80% of the code is from the third party and only 20% is original code. Even the softwares or application that checks the vulnerabilities of the codes do not give actual solution. We use third party libraries as set it and forget.

Question: Does this mean that just because the vulnerability resides in the library of some other person and not mine, can I be held responsible in case the data of my users is stolen?

<h2>A03:2021 - Injection</h2>

Injection is the next section, and it has swapped positions with OWASP Top 10 to position number 3. It is still not the vulnerability of the kingship, but it is one of the most dangerous as it gives the opportunity to the attackers to converse directly to your database or operating system.

<h2>Summary</h2>

The Issue: Injection occurs when an application mixes user input in code instructions. The application processes what a user types and runs it on the query accidentally.

The Scope: It was identified in 94 percent of applications that have been tested. It is not only on SQL, but also on NoSQL, LDAP, and even OS commands.

Common Failures: Make use of hostile information in search terms or file paths without removing special characters such as, semi-colon; zero-six.

Comment: Injection is attempting to be helpful and it is attempting to forward your message to the database, but it doesn't understand that the message has a concealed bomb. The drop of positioning of #1 to positioning of #3 is not that hackers had gone quiet; it is merely that contemporary tools have made it a great deal more difficult to make a mistake; only by making it a point to write out his own queries can one make an error.

Question: Can I be confident that I will be safe of Injection should I use a modern ORM (such as Entity Framework or Hibernate)?
